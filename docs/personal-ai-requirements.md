## 0. 한 줄 정의

> AX 풀스택 과정의 학습·프로젝트·공모전 활동을 **한 곳에 기록**하고, 로컬 LLM(Ollama)이 그 기록을 **기억**해서, 진행 상황 추적과 **포트폴리오 초안 생성까지 자동화**하는 개인용 시스템.

핵심은 "챗봇"이 아니라 **기록 + 검색 + 자동화 파이프라인**이다. LLM은 그 위에 얹는 인터페이스일 뿐이고, 가치의 80%는 데이터 구조에서 나온다. 이 순서를 뒤집으면(= 챗봇 먼저 만들면) 또 하나의 방치된 토이 프로젝트가 된다.

| 현재 문제 | 구체적 증상 |

## 2. 목표 / 비목표

### 2.1 목표 (to-be)
- **G1. 단일 진입점**: 하루 활동을 한 명령/한 파일로 기록한다. 기록 비용 < 2분/일.
- **G2. 영속 기억**: 나의 프로필·기술 스택·프로젝트 이력을 AI가 매번 설명 없이 알고 있다.
- **G3. 검색 가능**: 자연어로 과거 기록을 꺼낸다. ("Pandas groupby 처음 배운 날 뭐 했지?")
- **G4. 진행 상황 추적**: 프로젝트/공모전별 상태·마감일·다음 액션이 항상 최신으로 조회된다.
- **G5. 포트폴리오 자동화**: 기록을 입력으로 STAR 형식 프로젝트 설명 / 이력서 bullet / README 초안을 생성한다.
- **G6. 로컬 우선**: 개인 정보·미공개 공모전 아이디어가 외부로 나가지 않는다.

### 2.2 비목표 (이번 범위 아님)
- 모델 파인튜닝 / 자체 모델 학습 (RAG + 시스템 프롬프트로 충분. 파인튜닝은 ROI 최악)
- 팀 협업·멀티 유저
- 모바일 앱
- 24/7 서버 운영 (노트북 켤 때만 돌면 됨)
- 음성 인터페이스

## 4. 기능 요구사항

### FR-1. 기억 저장소 (Memory Store)
단일 진실 원천은 **플레인 텍스트 + Git**이다. DB를 1차 저장소로 쓰면 안 된다 — 커리어 자산을 특정 도구에 묶으면 도구 교체 시 전부 날아간다.

```
kant-study-lab/
├── memory/
│   ├── profile.md            # 나: 이름, 목표 직무, 강점, 선호 스타일
│   ├── skills.yaml           # 기술 스택 + 숙련도 + 근거(어느 프로젝트에서)
│   ├── goals.yaml            # 단기/장기 커리어 목표
│   └── decisions.md          # 중요한 선택과 이유 (왜 이 스택을 골랐나)
├── journal/
│   └── 2026/10/2026-10-10.md # 일일 로그 (프런트매터 + 본문)
├── projects/
│   └── <project-slug>/
│       ├── meta.yaml         # 상태, 기간, 역할, 스택, 마감, 성과지표
│       ├── log.md            # 진행 기록
│       └── artifacts/        # 산출물 링크·이미지
├── competitions/
│   └── <comp-slug>/meta.yaml # 공모전: 주제, 마감, 제출물, 결과
└── portfolio/
    ├── generated/            # AI 생성 초안 (사람이 검수 후 승격)
    └── final/                # 확정본
```

**일일 로그 스키마 (프런트매터)**
```yaml
---
date: 2026-10-10
type: journal
tags: [pandas, eda]
projects: [kant-study-lab]
mood: 3            # 1-5, 번아웃 조기 감지용
hours: {study: 4, project: 2}
---
## 배운 것
## 막힌 것 / 해결
## 다음 액션
```

- FR-1.1 모든 기록은 Markdown + YAML 프런트매터. 스키마는 문서화하고 검증 스크립트로 강제한다.
- FR-1.2 Git 커밋이 곧 변경 이력. 별도 버전관리 불필요.
- FR-1.3 민감 정보(미공개 공모전 아이디어 등)는 `private/` 하위에 두고 `.gitignore`로 분리하되 로컬 인덱싱 대상에는 포함한다.

### FR-2. 인덱싱 / 검색 (RAG)
- FR-2.1 `memory/`, `journal/`, `projects/`, `notebooks/`를 청킹해 벡터 임베딩한다.
- FR-2.2 `.ipynb`는 마크다운 셀 + 코드 셀 + 출력 일부를 텍스트로 추출해 인덱싱한다.
- FR-2.3 증분 인덱싱: 파일 해시 비교로 변경분만 재임베딩 (전체 재색인 금지 — 쌓이면 분 단위로 느려짐).
- FR-2.4 하이브리드 검색: 벡터 유사도 + 메타데이터 필터(날짜/태그/프로젝트). 날짜 질의("지난주")는 벡터 검색이 못 하므로 필터가 필수다.
- FR-2.5 응답은 **출처 파일 경로 + 날짜**를 함께 제시한다. 출처 없는 답은 환각 여부 판별 불가.

### FR-3. 대화 인터페이스
- FR-3.1 CLI 우선 (`kant ask "..."`, `kant log`, `kant status`). 터미널에 이미 살고 있으므로 가장 마찰이 적다.
- FR-3.2 시스템 프롬프트는 `memory/profile.md` + `skills.yaml` + 활성 프로젝트 요약을 **매 요청 시 주입**한다.
- FR-3.3 대화 이력은 세션 단위로 `journal/`에 저장 가능 (유용한 Q&A를 기록으로 승격).
- FR-3.4 (P2) Open WebUI 또는 Streamlit으로 GUI 제공.

### FR-4. 진행 상황 추적
- FR-4.1 `kant status`: 프로젝트/공모전을 마감일 순으로 출력. 상태(`idea|active|blocked|paused|done`), D-day, 마지막 업데이트 경과일.
- FR-4.2 **정체 감지**: 14일 이상 업데이트 없는 `active` 항목을 경고한다.
- FR-4.3 다음 액션은 각 `log.md`의 미완료 체크박스(`- [ ]`)에서 수집한다.

### FR-5. 포트폴리오 자동화
- FR-5.1 `kant portfolio <project>`: 해당 프로젝트의 meta + log + 관련 일일 로그를 전부 모아 아래 구조의 초안을 생성.
  - 한 줄 소개 / 문제 상황 / 내 역할 / 접근과 기술 선택 이유 / 결과(정량) / 트러블슈팅 1~2건 / 배운 점
- FR-5.2 **정량 지표 누락 시 비워두고 질문한다.** 수치를 추측해 채우면 면접에서 그대로 터진다 — 이건 타협 불가 요구사항.
- FR-5.3 산출물 형식: 프로젝트 README, 이력서 bullet(3~5줄), 자기소개서 소재 단락.
- FR-5.4 생성물은 `portfolio/generated/`에 떨어지고, 사람이 검수해 `final/`로 옮긴다. 자동 발행 금지.
- FR-5.5 (P2) `final/`을 정적 사이트로 빌드해 GitHub Pages 발행.

### FR-6. 자동화 / 스케줄
- FR-6.1 일일(저녁): 변경 파일 인덱싱 → 당일 로그 누락 시 알림.
- FR-6.2 주간(일요일): 주간 회고 초안 생성(배운 것 요약, 태그 분포, 정체 항목, 다음 주 제안) → `journal/`에 저장.
- FR-6.3 월간: `skills.yaml` 숙련도 근거 갱신 제안, 포트폴리오 갱신 대상 제안.
- FR-6.4 구현은 cron(macOS/Linux) 또는 작업 스케줄러. 실패 시 조용히 넘어가지 않고 로그를 남긴다.

## 6. 기술 스택 (제안)

| 레이어 | 선택 | 이유 |
|---|---|---|
| LLM 런타임 | **Ollama** | 요구사항. 모델 교체가 한 줄 |
| 생성 모델 | VRAM 8GB 이하: `qwen3:8b` / 16GB 이상: `qwen3:14b`·`gpt-oss:20b` | 한국어·코드 품질 대비 크기 |
| 임베딩 | `bge-m3` (한국어 강함) 또는 `nomic-embed-text` | 한/영 혼용 기록 대응 |
| 벡터 DB | **ChromaDB** (로컬 파일 모드) | 서버 불필요, 재구축 자유 |
| 언어 | Python 3.11+ | 과정에서 쓰는 언어와 통일 |
| CLI | Typer + Rich | 최소 코드로 쓸만한 UX |
| 오케스트레이션 | **직접 구현** (LangChain 미사용) | 기능 규모가 작고, 프레임워크 추상화가 디버깅을 더 어렵게 함. 더해서 "RAG를 직접 구현해봤다"가 포트폴리오로서 더 세다 |
| 스케줄 | cron / Task Scheduler | 의존성 0 |
| 패키지 | uv | 빠름 |

> 메타 관점: **이 시스템 자체가 AX 풀스택 포트폴리오 1순위 작품**이다. 로컬 LLM + RAG + 자동화 파이프라인 + CLI는 정확히 AI 엔지니어 JD의 교집합이다. 그러므로 구현 과정도 `projects/kant-ai/log.md`에 기록해야 한다 (자기 참조 구조).

## 7. 단계별 구현 계획

| Phase | 범위 | 완료 기준 | 예상 |
|---|---|---|---|
| **P0. 뼈대** | 디렉터리 구조, 스키마 정의, `memory/profile.md` 작성, `kant log` | 7일 연속 기록 성공 | 1일 |
| **P1. 기억하는 AI** | Ollama 연동, 시스템 프롬프트 주입, `kant ask` | 내 프로젝트 맥락 반영한 답변 | 2~3일 |
| **P2. 검색** | 인덱서 + Chroma + 하이브리드 검색, 출처 표시 | 과거 기록 질의 정확히 응답 | 3~4일 |
| **P3. 추적** | `meta.yaml` 파서, `kant status`, 정체 감지 | 진행 상황 한눈에 조회 | 2일 |
| **P4. 포트폴리오** | `kant portfolio`, 템플릿, 지표 질의 | 프로젝트 1건 초안 생성 성공 | 3일 |
| **P5. 자동화** | cron, 주간 회고 생성 | 사람 개입 없이 주간 회고 생성 | 2일 |
| **P6. 발행** | GUI, GitHub Pages | 공개 포트폴리오 URL 확보 | 선택 |

**P0 이후에는 반드시 7일간 실사용 후 P1으로 넘어간다.** 기록 습관이 안 붙은 상태에서 기능을 쌓으면 입력이 없는 시스템을 만들게 된다.

## 9. 결정 대기 항목

| # | 질문 | 왜 필요한가 |
|---|---|---|
| Q1 | 개발 머신 OS와 RAM/VRAM(GPU 모델)? | 생성 모델 크기와 응답 속도 상한이 여기서 결정됨 |
