# Kant AI — 요구사항 정의서 v1.0

작성일: 2026-10-10
근거: [`findings.md`](./findings.md) — 노션 TIL 21건, 깃허브 9개 레포, M1 Air 8GB 실측 기준
상태: 확정 대기 (§10 참조)

## 0. 한 줄 정의

> **노션에 쌓이는 학습 기록과 깃허브에 쌓이는 작업물을 이어 붙여서**, 검색·진행 추적·포트폴리오 초안 생성을 자동화하는 로컬 우선 개인 AI.

### v0.1에서 바뀐 것

실제 데이터를 읽고 네 가지를 뒤집었다.

1. **새 기록 체계를 만들지 않는다.** 노션 TIL DB가 이미 잘 설계돼 있고 21건이 쌓여 있다. 이중 기록은 반드시 실패하므로 노션이 단일 진실 원천이다.
2. **벡터 DB를 쓰지 않는다.** 21건이다. 1년 뒤에도 수백 건이다. 이 규모에서 ChromaDB는 순수한 과설계이고, 8GB 머신에서는 비용까지 든다. SQLite FTS5 + numpy 코사인으로 충분하다.
3. **생성 모델을 4B급으로 내린다.** 8GB 통합 메모리에서 8B는 스왑을 일으킨다.
4. **문제가 "기록 습관"이 아니다.** 노션에 기록은 되고 있다(29%). 작동하지 않는 것은 *기록 다음에 일어나야 할 일*이다 — 복습 필요 14건이 해소되지 않고, Unsolved 4건이 방치되고, 작업물이 포트폴리오로 가공되지 않는다. **이 시스템은 기록 도구가 아니라 밀어주는(push) 도구다.**

## 1. 목표 / 비목표

### 목표
- **G1. 연결**: 노션 TIL과 깃허브 레포/커밋/이슈를 하나의 인덱스로 합친다. (F-6 해소)
- **G2. 검색**: 자연어로 과거 기록을 꺼낸다. 출처와 날짜를 함께 제시한다.
- **G3. 밀어주기**: 복습 필요·Unsolved·정체된 프로젝트를 **먼저 알려준다**. 조회를 기다리지 않는다. (F-1, F-2 해소)
- **G4. 진행 추적**: 프로젝트/공모전의 상태·마감·다음 액션을 한 명령으로 본다.
- **G5. 포트폴리오**: 노션 기록 + 깃허브 실체를 묶어 STAR 형식 초안을 생성한다.
- **G6. 데이터 주권**: 노션이 죽어도 모든 기록이 내 디스크와 Git에 남는다.
- **G7. 로컬 우선**: 기본 전량 로컬 처리. 외부 전송은 명시적 플래그로만.

### 비목표
- 파인튜닝 / 자체 모델 학습
- 노션 대체 UI (노션에 쓰는 건 노션에서)
- 멀티 유저, 모바일 앱, 24/7 서버
- 음성 인터페이스

## 2. 데이터 아키텍처

### 2.1 역할 분리 (가장 중요한 결정)

| 레이어 | 담당 | 쓰기 주체 |
|---|---|---|
| **노션 TIL DB** | 일일 학습 기록의 진실 원천 | 사람 (기존 습관 유지) |
| **깃허브** | 작업물·커밋·이슈의 진실 원천 | 사람 (기존 습관 유지) |
| **`mirror/`** | 위 둘의 로컬 사본 (Markdown + JSON) | 수집기 (단방향, 읽기 전용 파생물) |
| **`index.db`** | 검색 인덱스 (SQLite FTS5 + 임베딩) | 인덱서 (언제든 재생성 가능한 캐시) |
| **`memory/`** | 프로필·목표·결정 로그 — 노션에 없는 것만 | 사람 + AI 제안 |
| **`portfolio/`** | 생성물 | AI 초안 → 사람 검수 |

**단방향 규칙**: 수집기는 노션과 깃허브에서 **읽기만** 한다. 쓰기는 하지 않는다. 이유 — 양방향 동기화는 충돌 해소 로직을 요구하고, 그 복잡도가 이 프로젝트 전체보다 크다. 노션에 쓸 일이 생기면 사람이 노션에서 쓴다.

> **예외 승격 경로**: `mirror/`는 파생물이지만 Git에 커밋한다. 노션 장애·요금제 변경·계정 사고 시 이것이 유일한 백업이 된다 (G6).

### 2.2 디렉터리

```
kant-ai/
├── docs/
│   ├── requirements.md      # 이 문서
│   └── findings.md          # 현황 분석
├── memory/
│   ├── profile.md           # 나: 목표 직무, 강점, 학습 스타일
│   ├── goals.yaml           # 단기/장기 목표
│   └── decisions.md         # 기술 선택과 그 이유
├── projects/                # 노션에 없는 프로젝트 메타 (F-5 보완)
│   └── <slug>.yaml          # 상태, 역할, 스택, 마감, 성과지표, repo, notion_url
├── mirror/                  # 수집 결과 (단방향, 커밋 대상)
│   ├── notion/til/<page_id>.md
│   └── github/<repo>.json
├── portfolio/
│   ├── generated/           # AI 초안
│   └── final/               # 사람 검수 완료
├── src/kant/
│   ├── sources/             # notion.py, github.py
│   ├── index.py             # FTS5 + 임베딩
│   ├── llm.py               # Ollama 래퍼 (모델 생명주기 관리)
│   ├── nudge.py             # 밀어주기 규칙 엔진
│   └── cli.py
└── index.db                 # .gitignore (재생성 가능)
```

## 3. 기능 요구사항

### FR-1. 수집 (Collect)
- **FR-1.1** 노션 TIL DB 전체를 페이지 본문까지 Markdown으로 내려받아 `mirror/notion/til/`에 저장. 프런트매터에 모든 속성 보존.
- **FR-1.2** `last_edited_time` 비교로 증분 수집. 변경된 페이지만 재요청.
- **FR-1.3** 깃허브 9개 레포의 메타·커밋 이력·open issue를 `mirror/github/`에 저장.
- **FR-1.4** `.ipynb`는 마크다운 셀 + 코드 셀을 텍스트로 추출. 출력은 길이 제한 후 포함.
- **FR-1.5 (날짜 검증)** 제목에서 날짜 패턴(`26.8.25.` 등)을 파싱해 `날짜` 속성과 비교. 불일치 시 `kant doctor`가 목록으로 보고한다. **자동 수정하지 않는다** — 어느 쪽이 맞는지 알 수 없으므로 사람이 정한다. (F-3)
- **FR-1.6** private 레포(`love-quiz-site`)도 수집한다. 미러는 비공개 레포에 두므로 안전하다.

### FR-2. 인덱싱 / 검색
- **FR-2.1** SQLite FTS5 전문 인덱스. 한국어는 `unicode61` + bigram 토크나이저로 처리 (형태소 분석기 의존성 없이).
- **FR-2.2** 임베딩은 `bge-m3`로 생성해 `.npy` 단일 배열로 저장. 질의 시 numpy 코사인 유사도 — 수백~수천 건 규모에서 벡터 DB보다 단순하고 빠르다.
- **FR-2.3** 하이브리드 검색: FTS5 키워드 점수 + 코사인 유사도를 가중 합산. **메타데이터 필터(날짜 범위, 카테고리, 이해도, 레포)는 벡터 검색 앞단에서 적용**한다 — "지난주"류 질의는 유사도로 풀 수 없다.
- **FR-2.4** 모든 응답은 출처(노션 URL 또는 깃허브 경로)와 날짜를 명시한다. 출처 없는 문장은 환각 여부를 판별할 수 없다.
- **FR-2.5** 증분 인덱싱. 파일 해시 비교로 변경분만 재임베딩.

### FR-3. 연결 (Link) — 이 시스템의 1차 목적
- **FR-3.1** TIL 레코드와 깃허브 레포/커밋을 연결한다. 1차 신호는 **날짜 근접성**(TIL 날짜 ±2일 내 커밋)과 **키워드 일치**.
- **FR-3.2** 자동 연결은 **제안**이고, 사람이 승인해야 확정된다. `projects/<slug>.yaml`에 기록된다. 추측으로 확정하면 포트폴리오에 거짓이 섞인다.
- **FR-3.3** `kant link` 로 미연결 TIL과 후보 레포를 짝지어 대화형으로 확인한다.

### FR-4. 밀어주기 (Nudge) — F-1·F-2 해소
- **FR-4.1** `kant nudge`가 아래를 우선순위 순으로 출력한다:
  - Unsolved = true 인 항목 (현재 4건), 오래된 순
  - 이해도 = "복습 필요"이고 기록 후 14일 경과한 항목 (현재 14건 중 대부분 해당)
  - `active` 상태인데 21일간 커밋도 TIL도 없는 프로젝트
  - 마감 D-14 이내인 공모전
  - 7일 이상 TIL 기록이 없을 때의 공백 경고
- **FR-4.2** 복습 필요 항목은 **한 번에 하나만** 제시한다. 14건을 동시에 보여주면 압도당해서 하나도 안 한다.
- **FR-4.3** 복습 완료 처리는 사람이 노션에서 한다. 시스템은 다음 수집 때 변화를 감지해 목록에서 제거한다.

### FR-5. 진행 추적
- **FR-5.1** `kant status`: 프로젝트/공모전을 마감일 순으로. 상태(`idea|active|blocked|paused|done`), D-day, 마지막 활동 경과일, 연결된 레포의 최근 커밋.
- **FR-5.2** 다음 액션은 깃허브 open issue(현재 8건)와 `projects/*.yaml`의 미완료 체크박스에서 수집한다.

### FR-6. 포트폴리오 생성
- **FR-6.1** `kant portfolio <slug>`: 연결된 TIL 기록 + 커밋 이력 + 레포 README + `projects/<slug>.yaml`을 모아 초안을 만든다.
  구조: 한 줄 소개 / 문제 / 내 역할 / 기술 선택과 이유 / 결과(정량) / 트러블슈팅 1~2건 / 배운 점
- **FR-6.2 (타협 불가)** **정량 지표가 데이터에 없으면 비워두고 질문한다.** 추측해서 채우지 않는다. 꾸며진 수치는 면접에서 그대로 터진다. 이 규칙은 어떤 편의성보다 우선한다.
- **FR-6.3** 난이도 ⭐⭐⭐⭐ 이상 + 배포 이력이 있는 항목을 우선 대상으로 제안한다. 현재 후보: `qrcode-checkout`(배포), `love-quiz-site`(배포), AX 평가 시스템(⭐⭐⭐⭐), 개인 지출 관리(⭐⭐⭐⭐⭐), 한국어 텍스트 분류(⭐⭐⭐⭐⭐).
- **FR-6.4** 산출물 3종: 레포 README / 이력서 bullet 3~5줄 / 자기소개서 소재 단락.
- **FR-6.5** `portfolio/generated/`에 저장. 사람이 검수해 `final/`로 승격. 자동 발행 금지.
- **FR-6.6 (P6)** `final/`을 기존 `my_profile` 레포로 발행.

### FR-7. 대화 인터페이스
- **FR-7.1** CLI 우선. `kant ask "..."`, `kant search`, `kant status`, `kant nudge`, `kant sync`, `kant doctor`, `kant link`, `kant portfolio`.
- **FR-7.2** 시스템 프롬프트에 `memory/profile.md` + 활성 프로젝트 요약 + 최근 TIL 5건을 매 요청 주입.
- **FR-7.3 (P6, 선택)** Streamlit GUI.

### FR-8. 자동화
- **FR-8.1** 일일(저녁 21시): `kant sync` → 인덱싱 → 변화 있으면 터미널 알림.
- **FR-8.2** 주간(일요일): 주간 회고 초안 생성 — 배운 것 요약, 카테고리 분포, 해소/신규 Unsolved, 정체 항목, 다음 주 제안 1개.
- **FR-8.3** launchd(macOS) 사용. 실패를 조용히 삼키지 않고 로그를 남긴다.

## 5. 기술 스택

| 레이어 | 선택 | 이유 |
|---|---|---|
| LLM 런타임 | **Ollama** | 요구사항 |
| 생성 모델 | **`qwen3:4b`** (q4_K_M, ~2.6GB) | 8GB에서 스왑 없이 도는 상한. 한국어 양호 |
| 임베딩 | **`bge-m3`** (~1.2GB) | 한/영 혼용 기록에 강함 |
| 모델 생명주기 | **`keep_alive: 0`** | 호출 후 즉시 언로드. 동시 상주 방지 (NFR-1) |
| 저장/검색 | **SQLite FTS5 + numpy** | 데이터 수백 건 규모. 벡터 DB는 과설계 |
| 언어 | Python 3.11+ | 과정에서 쓰는 언어 |
| CLI | Typer + Rich | 최소 코드로 쓸만한 UX |
| HTTP | httpx | Notion/GitHub/Ollama 공통 |
| 오케스트레이션 | **직접 구현** (LangChain 미사용) | 규모가 작고, 추상화가 디버깅을 어렵게 함. "RAG를 직접 구현했다"가 포트폴리오로 더 강함 |
| 스케줄 | launchd | macOS 네이티브, 의존성 0 |
| 패키지 | uv | 빠름 |

### 5.1 모델 티어링 (8GB 제약의 귀결)

| 작업 | 실행 위치 | 이유 |
|---|---|---|
| 임베딩 생성 | 로컬 (bge-m3) | 배치, 한 번만 |
| 검색 결과 재순위 | 로컬 (qwen3:4b) | 짧은 입출력 |
| 질의 응답 | 로컬 (qwen3:4b) | 짧은 답변이면 충분 |
| 태깅·분류 제안 | 로컬 (qwen3:4b) | 구조화 출력, 짧음 |
| **포트폴리오 초안** | **클라우드 (`--cloud`)** | 장문 한국어 품질이 중요. 4B로는 부족 |
| **주간 회고 생성** | **클라우드 (`--cloud`)** | 입력 컨텍스트가 큼 |

클라우드로 나가는 것은 이 두 가지뿐이고, 매번 명시적 플래그가 필요하다. 로컬만으로도 전체가 동작하며, 품질이 낮을 뿐이다. 이것이 G7(로컬 우선)과 현실(4B의 장문 한국어 한계)을 모두 지키는 타협점이다.

## 6. 단계별 구현 계획

| Phase | 범위 | 완료 기준 | 예상 |
|---|---|---|---|
| **P0. 수집** | 노션/깃허브 수집기, `mirror/`, `kant sync`, `kant doctor` | 21건 TIL + 9개 레포가 로컬 Markdown으로 떨어지고, 날짜 불일치 2건이 보고됨 | 2일 |
| **P1. 검색** | FTS5 + 임베딩 + 하이브리드 + 출처 표시 | "pandas 처음 배운 날" 질의에 정확한 출처 응답 | 3일 |
| **P2. 밀어주기** | `kant nudge` 규칙 엔진 | Unsolved 4건 + 복습 필요 항목이 하나씩 제시됨 | 1일 |

**P0→P2까지가 핵심이다.** 수집·검색·밀어주기만 되어도 현재 문제의 대부분이 풀린다. P3 이후는 포트폴리오를 위한 것이고, 과정 공부 시간을 침식하면 본말전도다.

### 메타: 이 프로젝트 자체가 포트폴리오 1순위
로컬 LLM + RAG + 외부 API 연동 + 자동화 파이프라인 + CLI는 AI 엔지니어 JD의 교집합이다. 세 직무(데이터 분석 / AI 엔지니어 / 풀스택)를 모두 노린다면 **가장 강한 단일 작품**이 된다. 따라서 구현 과정도 노션 TIL에 기록해야 한다 (자기 참조 구조).
